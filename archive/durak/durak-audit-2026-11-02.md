# Отчёт аудита игры «Дурак»

**Дата:** 2 ноября 2026 г.  
**Проверенная версия:** `61de7c4` (`Add multiplayer Durak game`)  
**Объём:** движок и правила, хранилище/ставки/выплаты, Durak API, интерфейс и имеющиеся тесты.  
**Итог:** критических путей к чужим картам или прямому управлению чужой партией при проверенном API не обнаружено. Найдены существенный риск для экономики игры с ботами, дефект перевода, некорректная обработка ничьей и пробелы в учёте/UX. Рекомендуется устранить P1 до широкого запуска.

## Краткое резюме

| Приоритет | Количество | Кратко |
|---|---:|---|
| **P1 — высокий** | 2 | Ботам не списывается взнос, но их ставки входят в призовой фонд; при переводе не пересчитывается лимит карт для нового защитника. |
| **P2 — средний** | 4 | Ничья скрывается интерфейсом и не попадает в историю; нельзя выйти из чужого ожидающего стола; незафиксированные/ограниченные сценарии идемпотентности и большие суммы; тестовое покрытие мало для многопользовательской игры. |
| **P3 — низкий** | 1 | Нет явной политики тайм-аута/выхода из партии; ожидание и возврат могут занимать до суток. |

## Находки

### P1. Бот-столы могут создавать монеты из воздуха

**Где:** `app/services/durak_store.py:104–142, 350–364`; выплаты — `153–213`.

При старте ставка списывается только с участников, у которых есть `user_id` (`humans`, строки 114–125). В бот-партии реальный участник один, остальные места — боты (`350–354`). При выплате доли, однако, считаются от полного числа мест: `payouts_by_place(count, stake)`, то есть как будто каждый бот внёс ставку.

Например, в столе на двоих победитель получает 2× ставку, хотя в банк поступила только одна реальная ставка. В столе на шестерых первое место получает 3× ставку при одном реальном взносе. Это может быть намеренной субсидией от «дома», но сейчас интерфейс описывает взнос как взнос каждого игрока, не объясняет, что ботские места финансируются системой, и не показывает размер этой субсидии. При удачной игре это инфляция внутреннего баланса; если баланс используется для других ставок/вывода — финансовый риск выше.

**Рекомендация:** явно выбрать и закрепить экономическую модель. Либо ботам начислять виртуальные взносы из отдельного house-банка с лимитами и отдельным ledger, либо считать призовой фонд только из фактически списанных ставок и заранее показывать формулу. Добавить тесты на баланс системы для выигрыша/проигрыша во всех размерах бот-стола.

### P1. При переводе не применяется лимит руки нового защитника

**Где:** `app/services/durak.py:327–336, 399–417`; лимит задаётся в `369`, используется в `290–296` и `409`.

`defender_hand_cap` фиксируется для первого защитника. При переводе меняется `state["defender"]`, но лимит не пересчитывается по картам нового защитника. В результате на нового игрока можно перенести и подкинуть больше карт, чем он имел в руке при принятии защиты. `legal_actions` тоже проверяет старый лимит. Это может навязать защиту, которую по ожидаемым правилам переводного Дурака нельзя было навязать.

**Рекомендация:** при переводе вычислять допустимый предел для нового защитника и ограничивать перевод/подкидывание по правилам выбранного варианта. Зафиксировать правило явно (включая ситуацию, когда у следующего защитника карт меньше, чем уже лежит на столе) и покрыть тестами с разными размерами рук и несколькими переводами.

### P2. Ничья рассчитывается, но теряется для игрока и в истории

**Где:** `app/services/durak_store.py:153–173, 463–470, 276–278`; `app/web/static/app.js:7663–7674`.

При повторе позиции движок завершает игру ничьей и хранилище возвращает ставки, помечая строку статусом `draw`. Но:

- ответ API выставляет `finished` только для статуса `finished`, поэтому для `draw` он ложный;
- выборка `state()` ищет текущие игры со статусом `active`/`waiting`, а последнюю партию — только со статусом `finished`; `draw` не попадает ни туда, ни туда;
- интерфейс показывает доску только при `status === "active"` и историю только из `last`.

Игрок получает возврат баланса, но после ничьей его итоговый экран/результат исчезает. Счётчик завершённых партий также не учитывает ничью. Код возврата ставки не создаёт запись в истории `casino_bets`.

**Рекомендация:** считать `draw` завершённым исходом во всех ответах, истории и UI; показывать «Ничья — ставки возвращены». Записывать отдельный результат/ledger для ничьих и возвратов, чтобы результат можно было проверить.

### P2. Нет выхода для присоединившегося игрока из ожидающего приватного стола

**Где:** `app/services/durak_store.py:429–435`; UI лобби — `app/web/static/app.js:7680–7710`.

Операция `cancel` разрешена только владельцу и только для стола в ожидании. В лобби кнопку закрытия получает только владелец. Другой игрок, который вошёл по коду, не может покинуть стол. Поскольку проверка `_find_busy` запрещает этому игроку создавать/вступать в другой стол, он может оказаться заблокированным до старта владельцем или истечения 24 часов.

**Рекомендация:** добавить `leave` для участника ожидающего стола (с безопасным удалением места и обновлением состояния) и явно обрабатывать уход владельца. Для уже начавшейся партии предусмотреть правила отключения/автохода/тайм-аута.

### P2. Недостаточная идемпотентность повторных ходов

**Где:** `app/services/durak_store.py:452–468`.

Хранится только последний токен действия на пользователя (`last_tokens`). Повтор непосредственно последнего запроса безопасен, но более старый токен забывается после следующего хода этого же пользователя. Если старый запрос будет повторно отправлен, когда очередь снова дойдёт до игрока, сервер может рассмотреть его как новое действие (если оно легально в текущей фазе). Это прежде всего риск неожиданного хода при сетевых повторах/повторной отправке, а не обход проверки принадлежности партии.

**Рекомендация:** хранить набор/последовательность уже обработанных токенов на игру с ограниченным размером либо монотонный номер хода и привязанный к нему idempotency key; проверять повтор до применения действия. Тестировать повтор запроса после нескольких ходов и после рестарта.

### P2. Нет безопасной верхней границы выплаты для BIGINT при больших балансах

**Где:** `app/services/durak.py:511–523`; списание и зачисление — `app/services/durak_store.py:117–125, 180–185`; API-конвертация — `app/web/server.py:1393–1403`.

Ставка ограничена диапазоном signed BIGINT на входе API и балансом игрока, но пул и индивидуальная выплата умножаются на количество мест. Сумма выплаты может превысить максимальное значение BIGINT даже при допустимой ставке и балансе. Например, в двухместной игре победителю причитается 2× ставку; база не сможет сохранить такой баланс, и расчёт завершится ошибкой транзакции.

Это крайний сценарий для текущих балансов, но особенно важен из-за требования не устанавливать верхний лимит ставки.

**Рекомендация:** либо хранить денежные значения в типе с более широким диапазоном, либо проверять достижимость всех возможных выплат до старта и отклонять небезопасную ставку понятной ошибкой. Граница должна рассчитываться по максимальной выплате для конкретного количества участников, а не произвольным UI-лимитом.

### P2. Durak-тесты не покрывают ключевые API и денежные сценарии

**Где:** `tests/test_durak_engine.py`, `tests/test_durak_store.py`.

Существующие тесты полезны и весь проект проходит, но Durak-набор небольшой: нет проверок HTTP-маршрутов/авторизации, многопользовательской последовательности с реальными аккаунтами, перевода при разном количестве карт, ничьей от начала до UI/истории, ухода игрока, повторного старого токена, а также сверки общей суммы списаний/выплат для бот-столов и больших значений.

**Рекомендация:** добавить интеграционные тесты на указанные случаи и property-based проверки инвариантов: колода не дублирует карты; скрытые карты не выдаются оппоненту; сумма выплат онлайн-партии равна сумме взносов; число мест и рейтинг уникальны; повторная обработка не меняет баланс повторно.

### P3. Партия без хода замораживает ставки на срок до суток

**Где:** `app/services/durak_store.py:229–264`.

Зависшие активные партии отменяются и ставки возвращаются после 24 часов без обновления. Это предотвращает вечную блокировку денег, но не позволяет сопернику быстро продолжить или завершить партию. Один игрок может оставить приложение, удерживая стол и баланс остальных на длительное время.

**Рекомендация:** определить и показать правила хода по времени. Рассмотреть более короткий таймер, предупреждение и действие по тайм-ауту (например, автоход/поражение/возврат в зависимости от состояния партии), согласовав последствия для ставок.

## Положительные контроли

- API требует Telegram initData через общий auth middleware; dev-режим относится к настройке приложения и должен быть выключен в production.
- Ход проверяется сервером по участнику, очереди и фазе; руки соперников не включаются в публичный ответ.
- Запросы к БД параметризованы; ставки списываются условным `UPDATE ... balance >= stake` внутри транзакции.
- Операции записи сериализуются; на PostgreSQL используется advisory transaction lock.
- Приватный стол нельзя открыть по одному `game_id` постороннему участнику — нужен код комнаты.
- Текущие проверки проекта: **742 теста пройдены**; `node --check`, `compileall` и `git diff --check` также прошли.

## Ограничения проверки

Это статический аудит исходников и проверка имеющихся тестов на коммите `61de7c4`. В рамках этого аудита не выполнялись внешний пентест, нагрузочное тестирование, анализ production-БД и проверка фактически развёрнутого экземпляра. Поэтому отчёт описывает код указанного коммита, а не подтверждает, что именно он уже работает на production.

## Рекомендуемый порядок исправлений

1. Решить экономическую модель бот-столов и закрыть вопрос субсидирования/баланса.
2. Исправить лимит руки при переводе и добавить тесты на цепочки переводов.
3. Довести исход `draw` через API, историю и UI; записывать возврат в финансовую историю.
4. Добавить выход из ожидающего стола и политику отключений/тайм-аутов.
5. Укрепить идемпотентность и проверить пределы выплат для BIGINT.
6. Расширить интеграционное покрытие перед production-релизом.

## Статус исправления после аудита

На последующий запрос исправлен пункт **P1 «При переводе не применяется лимит руки нового защитника»** в локальной рабочей копии:

- перевод теперь разрешён, только если следующий защитник активен и у него достаточно карт для уже лежащей атаки плюс переводимой карты (с общим пределом шесть);
- после успешного перевода лимит подкидывания пересчитывается по руке нового защитника;
- интерфейсные `legal_actions` и серверная проверка используют один и тот же критерий; индекс переводимой карты валидируется до удаления карты из руки.

Добавлены тесты на отказ при недостаточной руке нового защитника, правильный новый лимит после допустимого перевода и ситуацию, когда у нового защитника больше шести карт. После последнего изменения: **745 тестов пройдены**; `compileall` и `git diff --check` прошли. Предыдущий полный прогон показывал предупреждение `PytestUnhandledThreadExceptionWarning` в существующем тесте восстановления Telegram/SQLite-снимка (`tests/test_telegram_sqlite_snapshot.py`), но в последнем прогоне оно не повторилось.

Это исправление пока находится только в рабочей копии и не следует считать опубликованным или развёрнутым.
